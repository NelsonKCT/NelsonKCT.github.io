Migrating Nine Services from Java 8 to 21

During my internship at Garmin, a fleet of backend services was still running Java 8 with a phaseout deadline approaching. I ended up driving the migration to Java 21 and Spring Boot 3 across nine distinct services, which in practice meant about fifteen running instances once you count a repair-service portal deployed separately in seven countries.

Let the machine do the mechanical part

The core tool was OpenRewrite. Its recipes handle the mechanical rewrites: javax to jakarta, deprecated API replacements, Spring Boot 2 to 3 configuration changes. Running a recipe takes minutes. What it buys you is not speed on any single service, but consistency across all of them: the same transformation applied the same way nine times, with no fatigue-induced typos on service number seven.

The real work is dependency archaeology

What the recipes cannot do is decide what to do with a transitive dependency that has no Jakarta-compatible release, or a build plugin pinned five major versions back by a comment that says "do not upgrade". Every service had two or three of these. The pattern that worked for me: upgrade the build first, get it compiling with tests red, then fix tests in dependency order rather than file order. Most "test failures" were really serialization or time-zone behavior changes surfacing, not broken logic.

Ship it like it never happened

Each service went through the normal release process: peer review, a test report from a teammate, change-request sign-off, then production deployment. We staggered services so no two migrated in the same window. The success criterion was silence: no user-facing behavior change, no incident. That is what happened, which makes for a boring story and a good migration.

What I would do differently

I did not capture build-time and dependency-count numbers before starting, so I can say the migration went smoothly but not exactly how much healthier the builds became. Capturing a baseline costs ten minutes and makes the after-story concrete. That lesson cost me nothing this time, but I will not skip it again.

The migration also created the perfect excuse to fix a longer-standing problem: nobody could see what these services were doing in production. That story is in the next post.
