Four Small Fixes That Calmed a Payment Service

The payment service handling our B2B platform's transactions had grown organically, and it showed: work was being redone on every request that should have been done once at startup. None of the four fixes below is clever. That is the point. High-traffic services are usually slowed by boring waste, and boring waste has boring cures.

1. Real connection pooling

Database connections were being managed with a legacy setup that predated the service's current traffic. Switching to HikariCP gave us a properly tuned pool with sane defaults, plus pool metrics we could actually watch after the observability rollout. Opening connections is exactly the kind of cost you want to pay rarely and reuse aggressively.

2. Read configuration once

Several code paths were re-reading configuration values on every request. Spring already solves this: inject the value once with @Value at construction time and hold it in a field. A config lookup is cheap; a config lookup multiplied by every request on a payment path is not.

3. One ObjectMapper to rule them all

Jackson's ObjectMapper was being instantiated inside request handling. Building one is expensive; the object is thread-safe for reads once configured. Making it a single shared instance removed a per-request allocation and the GC pressure that came with it. This might be the highest ratio of keystrokes-to-impact in the whole codebase: the diff is a few lines.

4. Cache the hot read path

One read-heavy query returned data that changes at most daily but was hitting the database on every call. A Redis cache with a one-day TTL matched the data's real change rate. Choosing TTL by the data's nature rather than by superstition meant no invalidation machinery was needed at all.

The honest footnote

I can tell you what these fixes removed structurally: per-request connection churn, redundant lookups, repeated allocations, unnecessary database load. What I cannot tell you is the p95 latency before and after, because I did not measure it before starting. On a later ticket I also went back and added the unit tests this service deserved, which is the other unglamorous fix every payment path needs. Measure first, then tune: I learned it here so you do not have to.
